# Resume Agent P1 需求文档

> 文档级别：P1 / 显著增强
> 前置条件：[P0 MVP](./resume-agent-p0-prd.md) 已通过阶段门槛
> 总览：[Resume Agent 总路线图](./resume-agent-roadmap.md)
> 更新日期：2026-08-22
> 核心关系：`1X → nY`、`nX → 1Y`、`nE → 1Y → X′`

## 1. P1 定位

P0 证明的是：一个当前简历 X 可以针对一个岗位 Y 生成可审核的新版本 X′。

P1 解决的是三个更高价值的问题：

1. 当前这份简历最适合哪些已保存岗位？`1X → nY`
2. 当前这个岗位最适合使用哪份已有简历？`nX → 1Y`
3. 能否不受当前简历限制，从全部真实经历中组合更合适的岗位版本？`nE → 1Y → X′`

P1 完成后，产品从“定岗简历 Agent”升级为“简历、经历与岗位之间的智能选择和组装系统”。

---

## 2. P1 目标

### 2.1 用户目标

- 从当前简历出发，比较多个已保存岗位并找到优先投递对象。
- 从当前岗位出发，比较多份简历并选择最佳基础版本。
- 将未放入当前简历的真实经历纳入 Agent 检索和组装。
- 让 Agent 自动检查定岗版本的页数和版面，并在受限轮次内修订。
- 任务可以跨刷新恢复，并能查看完整历史和审批记录。

### 2.2 产品目标

- 建立 X/Y/E 三类对象的双向入口。
- 建立正式的 Resume Version、Agent Run 和 Experience 数据层。
- 将全局 Agent Dock 扩展为真正的上下文调度入口。
- 增加多对象比较结果的解释和收敛路径。
- 建立用户偏好和事实确认的长期记忆。
- 建立可重复运行的 Agent Eval。

### 2.3 研发目标

- 继续保留 P0 和旧 JD Workflow。
- 数据库变更以新增表和新增可空字段为主，不破坏现有记录。
- 单 Agent 优先，不因多对象任务直接引入多 Agent。
- 写工具继续受审批和幂等约束。

---

## 3. P1 范围

### 3.1 In Scope

- 全页面上下文 Agent Dock。
- 持久化 Agent 任务和任务历史。
- `1X → nY` 岗位匹配和排序。
- `nX → 1Y` 简历选择和比较。
- 经历库 E。
- 从现有简历批量导入 E。
- 经历事实确认和证据强度。
- `nE → 1Y → X′` 组装式定岗简历。
- 自动 A4/PDF 版面检查和有限修订。
- 正式简历版本谱系和回滚。
- 用户偏好记忆。
- Agent 任务恢复、成本和步骤审计。
- 离线 Eval 数据集与结果报告。

### 3.2 Out of Scope

- 多岗位自动投递。
- nX/nY 全局投递策略优化。
- 基于投递结果的自动学习闭环。
- 多任务并行执行。
- 主动式通知和机会提醒。
- 多 Agent 团队。
- 自动生成大量周边求职内容。

## 4. 信息架构

## 4.1 简历编辑器：以 X 为中心

左侧仍保留：

```text
[简历编辑] [JD分析]
```

右侧 Agent 栏增加两种业务模式：

```text
[单岗位优化] [岗位匹配]
```

- 单岗位优化：P0 的 `1X → 1Y`。
- 岗位匹配：P1 的 `1X → nY`。

岗位匹配结果以纵向排名卡展示；点击“针对该岗位优化”后收敛回单岗位模式。

## 4.2 岗位页：以 Y 为中心

岗位详情增加“选择简历”工作台：

```text
当前岗位 Y
→ 读取候选简历 nX
→ 排序和解释
→ 选择基础 X
→ 进入 1X → 1Y
```

结果展示：

- 推荐简历。
- 各简历匹配优势和主要缺口。
- 是否可以直接使用。
- 是否建议从经历库重新组装。

## 4.3 经历库：以 E 为中心

新增一级页面“经历库”，主要模块：

- 实习经历。
- 项目经历。
- 校园/竞赛/论文。
- 作品与作品集。
- 技能与工具证据。
- 成果指标和统计口径。

每个经历素材都可被多个 X 复用，但原始事实只有一个权威来源。

## 4.4 全局 Agent Dock：关系调度

P1 支持识别三类目标：

```text
“这份简历适合哪些岗位？”        → 1X → nY
“这个岗位应该用哪份简历？”      → nX → 1Y
“从我的经历中为这个岗位组一版”  → nE → 1Y → X′
```

Dock 必须把解析出的关系、对象和约束显示给用户确认，不静默运行。

P1 继承 P0 的“悬浮身份卡 → 展开 Dock”交互，不改成常驻聊天窗：

- X/Y 选择器从 P0 单选升级为可搜索、多选，并显示已选数量。
- `1X → nY`：锁定一个 X，Y 选择器允许选择多个已保存岗位。
- `nX → 1Y`：锁定一个 Y，X 选择器允许选择多份已有简历。
- `nE → 1Y → X′`：在 X/Y 行增加经历 E 入口，但仍用结构化对象确认任务关系。
- 自然语言可以帮助筛选和设置偏好，但模型解析结果必须回填为可见的 X/Y/E 选择。
- 多对象比较结果进入专门工作台；Dock 只展示任务摘要、进度和入口。

## 5. 功能需求：1X → nY

### 5.1 匹配范围

P1 第一版只比较用户已保存且包含 JD 的岗位，不接外部招聘网站抓取。

筛选：

- 全部已保存岗位。
- 感兴趣/已投递等状态。
- 公司。
- 岗位名称关键词。
- 创建时间。

候选数量超过上限时，先用确定性规则过滤，再由 Agent 处理 Top N。

### 5.2 匹配结果

每个岗位展示：

- 推荐顺序。
- 综合匹配分作为辅助信息。
- 三个主要匹配证据。
- 两个主要缺口。
- 建议动作：直接投递/小幅优化/需要定制/不建议优先。
- 预计优化成本。

### 5.3 收敛动作

- `查看匹配原因`
- `针对该岗位优化`
- `加入投递计划`
- `暂不考虑`

点击定岗优化后，自动把当前 X 和选中 Y 带入 P0 流程，不重新输入。

### 5.4 验收

- 同一批岗位重复运行结果具备基本稳定性。
- 推荐理由必须引用当前 X 的证据。
- 不用单一模型分数代替解释。
- 至少支持对 10 个已保存岗位进行一次匹配任务。

---

## 6. 功能需求：nX → 1Y

### 6.1 候选简历

- 用户全部已保存简历。
- 可按更新时间、名称和已绑定岗位过滤。
- 排除空白或解析失败简历。
- 默认最多选择最近/相关的 Top N 进入 Agent 比较。

### 6.2 比较维度

- 岗位核心要求覆盖。
- 证据强度。
- 相关经历优先级。
- 表达完整度。
- 版面可调整空间。
- 需要修改的工作量。

### 6.3 输出

- 推荐基础简历 X。
- 备选简历和不推荐原因。
- “直接使用/小改/重组”的建议。
- 进入定岗优化。

### 6.4 验收

- 每个推荐都能说明为什么优于其他候选。
- 用户可以覆盖 Agent 选择。
- 用户选择后复用 P0，不创建平行的修改流程。

---

## 7. 功能需求：经历库 E

## 7.1 数据来源

- 从现有简历导入。
- 用户手动新增。
- 从 Agent 无证据提醒中补充。
- 从已确认的岗位版本反向沉淀，但必须用户确认。

## 7.2 经历对象

建议最小对象：

```ts
interface ExperienceItem {
  id: string
  userId: string
  type: 'internship' | 'project' | 'campus' | 'competition' | 'paper' | 'portfolio' | 'skill'
  title: string
  organization?: string
  role?: string
  startDate?: string
  endDate?: string
  summary: string
  bullets: ExperienceBullet[]
  tags: string[]
  sourceResumeIds: string[]
  verificationStatus: 'imported' | 'confirmed' | 'needs_confirmation'
  createdAt: string
  updatedAt: string
}
```

```ts
interface ExperienceBullet {
  id: string
  text: string
  factType: 'responsibility' | 'method' | 'tool' | 'result' | 'metric'
  evidenceNote?: string
  verificationStatus: 'confirmed' | 'needs_confirmation'
}
```

### 7.3 去重与冲突

- 从多份简历导入相似经历时提示合并。
- 同一指标出现不同数值时标记冲突，不自动选择。
- Agent 不得将 `needs_confirmation` 事实作为低风险 Patch。
- 合并、删除和修改经历需保留审计信息。

### 7.4 经历检索

- 结构化过滤：类型、时间、组织、标签。
- 语义检索：JD 要求与 bullet 相似度。
- 证据强度排序。
- 用户确认状态加权。

---

## 8. 功能需求：nE → 1Y → X′

Agent 需要完成：

1. 提炼 Y 的差异化要求。
2. 从 E 中检索候选事实。
3. 建立 Requirement—Evidence Map。
4. 选择保留、前置、弱化和暂不使用的 E。
5. 生成 Resume Plan。
6. 生成结构化 X′ 草稿。
7. 校验事实、重复和 schema。
8. 渲染并检查版面。
9. 必要时有限修订。
10. 用户审核后创建正式版本。

### 8.1 Resume Plan

必须展示：

- 推荐模块顺序。
- 选择的经历。
- 未选择的重要经历及原因。
- 每段经历的主要职责。
- 页数预算。
- 不能覆盖的 JD 要求。

### 8.2 用户控制

- 锁定某段经历必须保留。
- 手动加入或移除候选经历。
- 调整经历顺序后重新生成正文。
- 不批准前不创建版本。

---

## 9. 版面感知 Agent

### 9.1 新增工具

- `render_resume_draft`
- `check_resume_layout`
- `revise_resume_for_layout`

### 9.2 检查项

- 实际页数。
- 溢出。
- 孤行。
- 末页内容过少。
- 字号/行距低于阈值。
- 模块占比失衡。
- 图片和头像异常。

### 9.3 修订限制

- 最多 2 次版面修订。
- 优先压缩低优先级表达，不改事实。
- 不得自动删除被用户锁定的经历。
- 不得把字号和行距降到可读阈值以下。
- 每次修订都生成可审计 Patch。

### 9.4 渲染一致性

继续遵循项目 PDF 约定：

- 使用现有 HTML renderer。
- 官方 PDF 使用受控 Chromium。
- 不使用截图切片或 `window.print()`。
- 预览状态和官方 PDF 渲染保持一致。

## 10. Agent 架构升级

## 10.1 工具扩展

P1 新增工具：

- `list_candidate_jobs`
- `list_candidate_resumes`
- `get_experience_library`
- `search_experiences`
- `rank_jobs_for_resume`
- `rank_resumes_for_job`
- `compose_resume_plan`
- `render_resume_draft`
- `check_resume_layout`

工具按任务类型动态授权，Agent 不会在单次任务中获得全部工具。

## 10.2 规划

P1 仍使用单 Agent，但计划支持分支：

```text
识别关系类型
→ 获取候选集合
→ 必要时缩小集合
→ 对 Top N 深度评估
→ 选择/组装
→ 校验
→ 版面修订
→ 人工批准
```

停止条件按任务类型分别定义，不采用一个无限循环。

## 10.3 工具权限

- 只读工具：可自动执行。
- 草稿工具：可自动执行，但只产生临时工件。
- 写入工具：要求用户批准和幂等键。
- 删除工具：不提供给 Agent。

## 11. 持久化任务和记忆

## 11.1 建议新增数据

P1 允许新增：

- `agent_runs`：目标、上下文、状态、模型、成本、最终结果。
- `agent_steps`：用户可见阶段、工具、输入摘要、结果摘要和错误。
- `agent_approvals`：Patch/动作的接受、拒绝、编辑后接受。
- `experience_items` / `experience_bullets`。
- `resume_versions`：父版本、岗位、Agent Run 和版本说明。
- `user_agent_preferences`：用户明确保存的偏好。

旧 `resumes`、`applications`、`jd_analysis_records` 保持兼容。

## 11.2 短期记忆

- 服务端持久化活动任务状态。
- 页面刷新和设备切换后可继续。
- 工具 Observation 结构化存储。
- 原始敏感内容按最小需要保存。

## 11.3 长期记忆

仅保存用户明确同意、可解释复用的内容：

- 已确认经历事实。
- 默认页数、语言和风格。
- 必须保留的经历。
- 经常编辑后接受的表达偏好。

不得把单次拒绝直接推断成永久偏好。

---

## 12. 版本管理

P1 建立正式版本谱系：

```text
基础简历 X0
├─ 百度-AI产品经理-v1
│  └─ 百度-AI产品经理-v2
├─ 阿里-产品经理-v1
└─ 美团-商业产品经理-v1
```

需求：

- 查看父版本和生成原因。
- 查看 Agent Run 和被接受 Patch。
- 比较任意两个版本。
- 回滚为新版本，不覆盖历史。
- Application 关联具体版本。

## 13. 任务历史 UI

全局 Dock 增加“最近任务”入口；展开后以轻量浮层展示：

- 运行中。
- 待审核。
- 已完成。
- 失败。

任务详情显示：

- 用户原始目标。
- 使用的 X/Y/E。
- 执行步骤。
- 结果工件。
- 审批记录。
- 成本和耗时摘要。

不展示内部 Chain of Thought。

## 14. Eval

### 14.1 数据集

- 20—50 份经过匿名处理的真实 JD。
- 5—10 组简历/经历库。
- 覆盖 AI 产品、软件产品、互联网产品等目标岗位。
- 标注强证据、弱证据、无证据和不应写入项。

### 14.2 指标

- 关系识别正确率。
- 候选岗位/简历 Top-K 命中。
- Experience 检索召回和精度。
- Patch 证据覆盖率。
- 无依据内容率。
- 版面通过率。
- 用户建议接受率。
- 任务成功率、成本和延迟。

### 14.3 对照

- 当前 JD Workflow。
- P0 Agent。
- P1 多对象/经历库 Agent。

报告必须使用真实测试结果，不使用示例数字充当结论。

## 15. P1 验收

### 1X → nY

- 当前简历可以对至少 10 个已保存岗位排序。
- 每个 Top 结果都有简历证据和缺口。
- 可以一键进入 P0 定岗优化。

### nX → 1Y

- 当前岗位可以比较至少 5 份候选简历。
- 推荐结果可解释，用户可覆盖。
- 选定后复用同一 P0 流程。

### nE → 1Y → X′

- 用户可以从多份简历导入经历并去重确认。
- Agent 可以检索当前 X 之外的真实经历。
- 生成方案显示选择和舍弃理由。
- 新内容均绑定已确认 E。

### 任务和版面

- 活动任务可以跨刷新恢复。
- 自动版面修订不超过规定轮次。
- 每次修订可审计、可撤销。
- 正式版本可比较和回滚。

---

## 16. P1 发布策略

建议按以下顺序灰度：

1. 持久化 Agent Run 和版本谱系。
2. `1X → nY` 已保存岗位匹配。
3. `nX → 1Y` 已有简历选择。
4. 经历库导入和人工维护。
5. `nE → 1Y → X′`。
6. 自动版面修订。
7. 偏好记忆和 Eval Dashboard。

每个模块保留 feature flag；P0 定岗流程始终作为稳定回退路径。
