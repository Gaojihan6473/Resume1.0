# Resume Agent P2 需求文档

> 文档级别：P2 / 锦上添花与长期差异化
> 前置条件：[P1](./resume-agent-p1-prd.md) 已形成稳定数据和使用闭环
> 总览：[Resume Agent 总路线图](./resume-agent-roadmap.md)
> 更新日期：2026-08-22
> 核心关系：`nX → nY` 与长期求职策略

## 1. P2 定位

P2 不再只关注“如何完成一份定岗简历”，而是让 Agent 利用用户已经积累的简历版本、经历、岗位、任务和投递结果，辅助制定长期求职策略。

P2 的价值来自 P0/P1 的真实使用数据。如果前置阶段没有足够的：

- 经历库 E。
- 简历版本 X。
- 岗位 Y。
- Agent 审批记录。
- 投递状态和结果。

则 P2 不应提前开发或宣传“学习用户”。

---

## 2. P2 目标

### 2.1 用户目标

- 管理多个岗位和多个简历版本的投递策略。
- 知道哪些岗位值得优先投入定制成本。
- 利用历史结果改善后续经历选择和表达。
- 在关键节点获得主动但可控的提醒。
- 让同一套真实经历支持简历、求职信、面试和作品集准备。
- 允许后台同时处理多个耗时任务。

### 2.2 产品目标

- 从单任务 Agent 演进为个人求职任务系统。
- 建立可解释的长期反馈记忆。
- 建立 nX/nY 组合策略。
- 扩展多工件生成，但保持证据一致。
- 建立主动式 Agent、任务队列和通知。
- 建立成本、实验、隐私和记忆治理平台。

---

## 3. P2 范围

### 3.1 In Scope

- nX/nY 投递策略矩阵。
- 简历版本与岗位的推荐分配。
- 投递结果反馈和内容效果分析。
- 主动式提醒和下一步建议。
- 多任务队列和后台执行。
- 求职信、面试问题、项目讲解、作品集重点等工件。
- 全局 Agent 的更自然输入和生成式 UI。
- 长期记忆管理和用户控制中心。
- 个性化 Eval、实验和成本治理。

### 3.2 Out of Scope

- 无批准自动提交申请。
- 代替用户回答真实性、身份、薪资或签证问题。
- 基于小样本承诺面试/Offer 概率。
- 自动把相关性解释成因果。
- 默认抓取用户外部私人数据。
- 让 Agent 绕过招聘网站或浏览器安全限制。
- 为架构宣传而拆分多 Agent。

## 4. nX → nY 投递策略

## 4.1 用户问题

> 我有多份基础/岗位简历和多个目标岗位，应该把时间投入到哪里，分别使用哪个版本？

## 4.2 策略矩阵

系统生成可解释矩阵：

| 岗位 | 推荐简历 | 适配程度 | 定制成本 | 证据缺口 | 建议动作 |
|---|---|---|---|---|---|
| 百度 AI 产品经理 | AI 产品版 v3 | 高 | 低 | 模型 Eval 表达 | 优先投递 |
| 阿里软件产品经理 | 产品基础版 v2 | 中 | 中 | B 端经验 | 小幅定制 |
| 美团商业产品经理 | 暂无合适版本 | 低 | 高 | 商业闭环 | 暂缓/补充经历 |

## 4.3 策略约束

- 用户可设置每周可投入的定制时间。
- 用户可设置公司/岗位优先级。
- 已投递、截止时间和当前阶段影响排序。
- Agent 只能推荐，不自动放弃岗位。
- 推荐必须显示证据、缺口和不确定性。

## 4.4 收敛动作

- 为选中岗位创建定岗任务。
- 复用已有版本。
- 创建新版本。
- 暂缓并加入准备清单。
- 标记不考虑，并记录用户明确原因。

## 5. 投递结果反馈学习

## 5.1 关联对象

```text
Experience E
→ Resume Version X
→ Agent Run / Accepted Patches
→ Job Y
→ Application Status / Result
```

## 5.2 可分析问题

- 哪类经历在某类岗位中更常被使用。
- 哪些表达被用户频繁接受或编辑后接受。
- 哪类简历版本获得更多测评/面试。
- 哪些建议被频繁拒绝。
- 哪些岗位表面匹配高但投递效果弱。

## 5.3 归因原则

- 小样本只展示趋势，不下确定结论。
- 区分相关性和因果。
- 同时展示样本量、时间范围和岗位类型。
- 用户可以排除异常样本。
- 不将拒绝结果简单归因于简历质量。

## 5.4 个性化建议

示例：

```text
过去 8 次 AI 产品岗位投递中，包含“模型评测和用户反馈闭环”的版本有 4 次进入下一阶段。
该观察仅基于小样本，建议继续验证，而非自动改写所有版本。
```

## 6. 主动式 Agent

## 6.1 主动触发场景

- 岗位尚未关联简历。
- 关联简历使用的是旧 JD 分析结果。
- 当前投递使用了基础版而非岗位版。
- 截止日期临近但定岗任务未完成。
- 简历版本发生变化，相关岗位可能需要重新检查。
- 面试状态更新后尚未生成准备清单。

## 6.2 主动程度

用户可选择：

- 关闭主动建议。
- 仅关键风险。
- 标准建议。
- 更积极的求职提醒。

P2 默认使用“仅关键风险”，不得通过大量通知制造焦虑。

## 6.3 交互

主动建议显示为全局 Dock 的可忽略卡片：

- 为什么现在提醒。
- 使用了哪些数据。
- 建议动作。
- 稍后提醒。
- 不再提醒此类建议。

不自动执行写入或外部通信。

---

## 7. 多工件求职任务

所有工件继续以 E/X/Y 为共同事实来源。

## 7.1 求职信

- 基于目标岗位和已确认经历。
- 每个核心事实可追溯。
- 不复制简历全文。
- 用户审核后导出或复制。

## 7.2 面试准备

- 根据 JD、定岗简历和证据缺口生成问题。
- 生成项目追问、数据口径追问和真实性检查。
- 答案草稿必须引用真实经历。
- 不替用户编造行为和结果。

## 7.3 项目讲解稿

- 将经历整理成 STAR/业务问题—方案—结果结构。
- 标记需要用户补充的数据和决策背景。
- 与简历版本保持事实一致。

## 7.4 作品集重点

- 根据 Y 推荐展示哪些项目。
- 生成结构建议和准备清单。
- 不直接生成未经确认的项目成果。

## 7.5 工件一致性

若同一事实在简历、求职信和面试材料中表达冲突：

- 标记冲突。
- 回溯权威 Experience。
- 要求用户确认。
- 不自动覆盖所有工件。

---

## 8. 多任务队列和后台执行

## 8.1 队列

- 同一用户可创建多个任务。
- 限制同时运行数量。
- 任务状态：排队、运行、待审核、完成、失败、取消。
- 用户可调整优先级。

## 8.2 后台执行

- 任务不依赖前端页面持续打开。
- 使用持久化状态和幂等工具。
- 超时后可从最后安全步骤恢复。
- 所有写入仍等待审批。

## 8.3 通知

- 应用内通知为默认。
- 邮件/其他外部通知需要用户单独授权。
- 通知只包含非敏感摘要。
- 用户可控制通知类型和频率。

## 8.4 任务中心

展示：

- 活动任务。
- 待审核任务。
- 最近完成。
- 失败及恢复建议。
- 预计时间和成本范围。

---

## 9. 全局 Agent 交互升级

## 9.1 自然语言与结构化 UI

P2 在 P0/P1 Agent Dock 的基础上升级为全局命令 Dock：默认仍保持紧凑悬浮，不用常驻大输入框打断专业工作台；当任务已经超出 X/Y 单次选择时，才展开更完整的生成式交互。

Agent 回复优先使用业务卡片：

- 岗位卡。
- 简历版本卡。
- 经历证据卡。
- 任务计划。
- 比较矩阵。
- 审批动作。

文本对话用于补充，不替代专业工作台。

- 简历 X、岗位 Y、经历 E 继续作为可点击、可替换的结构化上下文。
- 允许在 Dock 内通过自然语言创建多步任务，但解析出的对象、范围、计划和外部动作必须可见。
- 下拉选择器可根据任务关系动态升级为单选、多选、搜索或比较选择器。
- 复杂任务的完整过程、比较矩阵和审批仍进入专门工作台，不无限增高 Dock。

## 9.2 上下文操作

- 拖入岗位卡、简历卡或经历卡。
- 在简历中框选内容后发起指令。
- 将文件添加为待解析素材。
- 使用快捷指令和历史任务模板。

## 9.3 语音

- 语音只作为输入方式。
- 转写后展示文本并允许修改。
- 涉及任务开始、数据写入和外部操作仍需显式确认。

## 9.4 生成式 UI 边界

- 只生成白名单组件和动作。
- 不允许模型输出任意 HTML/脚本。
- 所有动作参数经过 schema 校验。
- 关键操作使用固定组件和固定确认流程。

## 10. 长期记忆

## 10.1 记忆类型

- 事实记忆：已确认经历和成果。
- 偏好记忆：页数、风格、优先岗位、必须保留内容。
- 决策记忆：Patch 接受、拒绝和编辑后接受。
- 结果记忆：投递阶段和结果。
- 策略记忆：用户明确保存的求职方向和时间约束。

## 10.2 写入条件

- 事实记忆需要用户确认或来自权威记录。
- 偏好不能由一次行为永久推断。
- 敏感信息单独标记并限制用途。
- 记忆写入必须说明用途。

## 10.3 用户控制中心

用户可以：

- 查看 Agent 记住了什么。
- 修改或删除记忆。
- 暂停个性化。
- 选择哪些数据参与推荐。
- 导出个人数据。

删除记忆不应删除原始简历/岗位，除非用户明确选择对应对象。

---

## 11. Agent 架构演进

## 11.1 单 Agent 仍为默认

P2 任务复杂度增加，但优先通过：

- 任务类型路由。
- 按需工具授权。
- 子计划。
- 持久化状态机。
- 后台队列。

扩展单 Agent。

## 11.2 多 Agent 评估条件

只有满足以下条件才评估拆分：

- 单 Agent 工具集过大且选择准确率持续下降。
- 不同任务需要明显独立的上下文和权限。
- 有 Eval 证明拆分提高成功率或降低成本。
- 可以清楚定义交接协议和失败恢复。

禁止仅为了作品集宣传增加 Planner/Writer/Critic 等角色。

## 11.3 P2 工具域

- 策略工具：构建 nX/nY 矩阵和时间预算。
- 反馈工具：读取聚合投递结果。
- 工件工具：生成求职信、面试和作品集草稿。
- 通知工具：创建应用内提醒。
- 记忆工具：读取/建议写入长期记忆。

写记忆、发通知和创建外部工件都需要相应权限和确认。

---

## 12. 实验和成本治理

## 12.1 实验平台

- Prompt/模型/工具版本。
- 离线 Eval。
- 小流量灰度。
- 任务成功率和人工接管率。
- 版本回滚。

## 12.2 成本治理

- 不同任务类型设置预算。
- 候选集合先用规则/向量缩小，再用强模型深度分析。
- 缓存相同 hash 和版本的结果。
- 后台任务支持用户可见的预计成本或额度。
- 超出预算时返回 partial，不无限重试。

## 12.3 模型路由

- 简单分类和摘要使用低成本模型。
- 高风险事实校验和最终组装使用能力更强模型。
- 模型选择由服务端策略管理，不要求用户理解供应商细节。

---

## 13. 隐私与安全

- 记忆默认按用户隔离。
- 敏感简历内容最小化传输和存储。
- 外部连接器需要单独授权。
- JD、网页和上传材料均视为不可信内容。
- Agent 不能根据网页内容扩大工具权限。
- 自动通知不得泄露完整简历或个人联系方式。
- 高风险动作保留审计和撤销/补偿机制。

---

## 14. P2 指标

### 策略价值

- 推荐岗位被加入投递计划的比例。
- 推荐简历版本被采用的比例。
- 用户完成一组岗位分配所需时间。
- 高定制成本岗位被合理收敛的比例。

### 长期反馈

- 有足够样本的用户比例。
- 个性化建议被接受/修改/关闭的比例。
- 记忆查看、修改和删除率。
- 错误个性化反馈率。

### 主动式 Agent

- 主动建议打开率和完成率。
- 忽略率和关闭率。
- 通知投诉/打扰反馈。

### 多任务

- 队列任务成功率。
- 平均等待时间。
- 恢复成功率。
- 单用户日/月成本。

---

## 15. P2 验收原则

P2 各模块独立灰度，不设置一次性“大版本完成”门槛。每个模块必须证明：

1. 相比 P1 明显减少用户决策或执行成本。
2. 使用的数据获得授权且可解释。
3. 结果能回溯到 E/X/Y/历史任务。
4. 错误不会触发未经批准的外部或写入动作。
5. 用户可以关闭、撤销或修正 Agent 的个性化行为。
6. 有真实 Eval 和线上指标支持继续扩展。

---

## 16. 推荐实施顺序

1. 正式投递结果关联和样本质量治理。
2. nX/nY 策略矩阵。
3. 长期记忆控制中心。
4. 主动式关键风险提醒。
5. 多工件生成与事实一致性。
6. 后台多任务队列和应用内通知。
7. 自然交互和生成式 UI。
8. 基于 Eval 决定是否需要多 Agent。

每一步都必须保留 P0/P1 的手动和受控路径作为回退。
